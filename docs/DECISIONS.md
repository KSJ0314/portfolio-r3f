## 기록

### 001. 브랜치 전략: 풀 Git Flow 채택

- **날짜**: 2026-07-01
- **상태**: 채택
- **맥락**: `main` 머지가 자동 배포로 이어지므로, 미완성·부분 기능이 라이브 사용자에게 노출될 위험이 있다. 운영 시작 시점은 예측 불가하고, 운영 중에도 변경이 계속된다.
- **결정**: `main + develop + feature`(+ 운영 시 `release`·`hotfix`) 구조의 Git Flow 채택. `develop`을 통합·스테이징 버퍼로 사용. 개발 단계에서는 `feature → develop → main` 직접 승격, `release`·`hotfix`는 운영 시작 후 도입.
- **이유**: `develop`이 라이브(`main`)와 개발을 분리해, 릴리스된 것만 프로덕션에 노출되게 한다. 처음부터 깔아두면 운영 전환 시 구조 변경이 불필요하다.
- **영향**: 초기 셋업은 `develop`에 모여 `main`으로 승격. Vercel 스테이징(`develop`)에서 검증 후 프로덕션(`main`) 반영.

### 002. 배포/호스팅: GitHub Pages → Vercel

- **날짜**: 2026-07-01
- **상태**: 채택 (기존 GitHub Pages 결정을 대체)
- **맥락**: 릴리스를 라이브 반영 전에 배포 환경에서 검증할 스테이징/프리뷰가 필요하다. GitHub Pages는 레포당 사이트가 1개라 스테이징·프로덕션 분리와 PR 프리뷰를 기본 기능으로 제공하지 못한다.
- **결정**: 배포처를 **Vercel**로 변경.
- **이유**: 브랜치·PR별 자동 프리뷰 URL 제공(`main`=프로덕션, `develop`=스테이징, PR=프리뷰). Git 연동 자동 CI/CD라 별도 워크플로가 불필요하고, Vite/React DX가 우수하며, base 경로·SPA 문제가 해소된다.
- **영향**: 로드맵 Phase 0.5를 "GitHub Pages + Actions" → "Vercel 연결"로 변경. 배포 워크플로 직접 작성 불필요.

### 003. 카메라 이동 모델: 캐릭터 팔로우 + 우클릭 홀드 이동

- **날짜**: 2026-07-07
- **상태**: 채택
- **맥락**: 캐릭터 없는 항공뷰에서 이동을 어떻게 표현할지. 초기엔 "타겟 글라이드"(카메라가 클릭 지점을 화면 중앙으로) 고려.
- **결정**: 임시 캐릭터를 두고 카메라가 캐릭터를 따라가 화면 중앙 고정. 우클릭 홀드로 이동, 좌클릭은 인터랙션용 예약.
- **이유**: 화면상 캐릭터 고정 + 월드 스크롤이 동물의숲/춘식이 톤에 맞고, Phase 11 실제 캐릭터·걷기 애니메이션으로 자연 확장. 우클릭/좌클릭 분리로 이후 클릭 상호작용과 충돌 없음.
- **영향**: 이동은 고정 속도 per-frame step, gsap 단발 트윈 제거.

### 004. Orthographic 뷰 채택 (원근 제거)

- **날짜**: 2026-07-07
- **상태**: 채택
- **맥락**: Perspective(fov)는 원근감이 있어 "춘식이의 관찰일기"식 평면 아이소메트릭과 다름.
- **결정**: Orthographic 카메라 채택(fov 없이 zoom으로 배율).
- **이유**: 원근 왜곡 없는 균일한 아이소메트릭 뷰, 위치 무관 동일 크기로 가독성↑.
- **영향**: 배율은 zoom(현재 120), 전환 시 이전 perspective 배율에 맞춤.

### 005. 이동 경계: clamp(투명 벽) + 최종 "바닥 전체 + 투명 경계벽"

- **날짜**: 2026-07-07
- **상태**: 채택
- **맥락**: 제한된 영역만 이동하되 유저에게 맵 가장자리를 안 보이게.
- **결정**: 목표점을 CAMERA_BOUNDS로 clamp해 경계에서 정지(투명 벽). 현재는 맵을 크게 둬 가장자리 숨김, 최종은 바닥 전체 + 투명 경계벽.
- **이유**: 안정적 탐험 UX, 콘텐츠를 항상 화면에 잡음.
- **영향**: 텍스처는 바닥 전체에 적용.
- **갱신(2026-07-15)**: clamp 방식이 곧 최종이다. 바닥을 이동범위보다 크게 둬 가장자리가 안 보이므로 별도 물리 경계벽은 두지 않는다. 제목의 "최종 바닥 전체 + 투명 경계벽"은 이 clamp 구현을 가리키며, 추가 작업은 없다.

### 006. 스테이션 표현: 월드 내 고유 오브젝트 + 제자리 활성화 (Html-transform 벽 폐기)

- **날짜**: 2026-07-09
- **상태**: 채택 (기존 "2D 패널 = 월드에 뜬 벽" 모델 대체)
- **맥락**: 초기엔 모든 스테이션을 동일한 "월드에 뜬 벽"으로 두고, 인터랙션 시 카메라가 벽 정면으로 이동해 drei `<Html transform>`으로 2D DOM 패널을 띄우는 균일 모델을 가정했다.
- **결정**: 스테이션을 **각기 다른 고유 3D 오브젝트**로 만든다. 오브젝트 자체가 내용을 간략히 암시하는 미리보기이고, 좌클릭하면 **그 오브젝트가 제자리에서 활성화·확장**되어 상세를 보여준다. 상세 표현은 2D 패널로 한정하지 않고 **3D/혼합**도 허용한다. 공통층은 배치·근접·선택·미니맵·표지판뿐이고, 겉모습과 상세는 `스테이션 id → 전용 컴포넌트` 레지스트리로 스테이션마다 독립 구현한다.
- **이유**: 저폴리/아기자기 오픈월드 톤엔 균일한 벽보다 주제를 상징하는 오브젝트가 어울리고, 스테이션마다 표현·인터랙션이 완전히 달라도 서로 독립적으로 만들 수 있다. drei `<Html transform>`은 폐기가 아니라 상세가 2D일 때 쓰는 여러 옵션 중 하나로 격하된다.
- **영향**: PLAN의 "시그니처 경험 / 2D 패널=벽 / 프로젝트 전시 벽", 로드맵 Phase 3·4 문구를 오브젝트·활성화 모델로 갱신. Phase 2(배치)는 영향 적음 — 임시 오브젝트를 레지스트리에 등록해 프레임워크만 완성.
- **갱신(2026-07-15)**: 공통층 책임에서 표지판을 뺀다. 방향 안내(표지판·바닥 화살표)는 스테이션 실물이 생기는 Phase 8에서 스테이션별로 넣는다. 미사용이던 `SIGNPOSTS`·`Signpost`·`HUB`도 제거했다.

### 007. 스테이션 활성화: 라이프사이클만 공통층, 상세·카메라 연출은 스테이션별 전면 위임

- **날짜**: 2026-07-13
- **상태**: 채택
- **맥락**: 006에서 "스테이션마다 고유 오브젝트 + 제자리 활성화"로 정했지만, 활성화 이후의 상세와 카메라 연출을 공통 셸로 만들지 스테이션별로 만들지는 미정이었다. 공통 패널 셸 + 선언형 카메라 스펙(offset·zoom·duration)을 두는 안도 검토했다.
- **결정**: 공통층은 **활성화 라이프사이클**(`idle → entering → active → exiting`)·이동 잠금·마운트 자리·레지스트리 계약만 갖는다. 상세 UI와 카메라 연출은 전부 스테이션 구현의 몫이며 **공통 셸도 기본 구현체도 두지 않는다**. 활성화되면 공통층은 카메라 팔로우를 멈춰 **제어권을 스테이션에 넘기고**, 어떻게 움직이는지는 알지 못한다. 대신 닫힐 때 원래 오프셋·zoom으로 돌아오는 **복귀만 보장**한다.
- **이유**: 기본 구현체가 있으면 이후 스테이션들이 그 틀에 끌려간다. 카메라 연출도 스테이션마다 완전히 달라야 하므로 값 기반 선언형 계약조차 두지 않고, 트윈을 통째로 스테이션에 맡긴다.
- **상호작용 규칙**: 이동 잠금은 **애니메이션 재생 중(entering·exiting)에만** 걸린다. `active`에서 우클릭은 곧 종료 트리거이고, 클릭 지점을 기억해뒀다가 **종료 애니메이션이 끝난 뒤** 캐릭터가 그리로 출발한다. ESC로도 종료된다. 좌클릭은 상세 내부 요소 상호작용 전용이라 닫기에 쓰지 않는다.
- **계약**: 스테이션 구현은 `phase`를 받아 진입·종료 애니메이션을 재생하고, 끝나면 `enterComplete()`/`exitComplete()`로 공통층에 알린다. 등록된 구현이 없는 스테이션은 알릴 주체가 없으므로 공통층이 즉시 완료 처리한다.
- **한계(의도적으로 남김)**: 평상시 모습은 아직 `Station`의 공통 임시 박스이고, 활성화 시 마운트되는 상세 컴포넌트와 분리돼 있다. 그래서 같은 오브젝트가 이어서 변형되는 연출은 아직 만들 수 없다. 비활성 슬롯은 고유 오브젝트를 만드는 Phase 8에서 레지스트리에 추가한다.
- **갱신(2026-07-22) — 상호작용 규칙 교체**: 우클릭 종료를 폐기한다. 닫는 방법은 **근접 이탈 · 스테이션이 제공하는 나가기 요소 · ESC** 세 가지이고, 우클릭은 순수하게 이동이다. 활성 중에도 평소처럼 걸어다닐 수 있으며 **영역에서 멀어지는 것이 곧 닫기**다. 이동 잠금은 `entering`에만 건다 — 걸어나가는 것이 종료 트리거인데 `exiting`에 잠그면 그 자리에서 멈칫한다. 종료 후 이동을 위한 `pendingTarget`은 쓸 일이 없어져 제거했다.
- **갱신(2026-08-03) — 제어권 이양 시점**: 카메라 제어권은 활성화되는 순간이 아니라 **스테이션의 연출 이동이 끝날 때** 넘어간다. 스테이션은 진입 연출로 캐릭터를 자기 자리로 데려갈 수 있고(`useCameraStore.walkTo`), 걷는 동안에는 공통층이 평소처럼 팔로우한다. 카메라를 먼저 세워두고 캐릭터만 움직이면 걸어가는 모습이 화면 밖으로 밀린다. 이동 잠금은 그대로 걸리되 이 연출 이동만 예외로 통과하며, 도착 판정은 이동을 맡은 `Character`가 한다.
- **갱신(2026-07-22) — 한계 해소**: 레지스트리에 `Inactive`(비활성 상태, 상시 마운트) 슬롯을 추가해 비활성 모습도 스테이션이 직접 그린다. 근접 거리 계산을 맡기는 `distanceTo`도 함께 추가했다(DECISIONS 014). 스테이션이 부드럽게 복귀하려면 현재 카메라 자세를 보지 말고 `useCameraStore.followOffset`으로 복귀 자세를 계산해야 한다.

### 008. 아트 디렉션 전환: 저폴리 파스텔 마을 → 스케치북

- **날짜**: 2026-07-14
- **상태**: 채택 (기존 "저폴리 + 파스텔, 아늑한 섬/마을" 방향 대체)
- **맥락**: 기존 아트 방향은 동물의 숲·춘식이 톤의 아기자기한 마을이었다. 그러려면 나무·집·소품 등 배경 에셋을 대량으로 소싱하거나 모델링해야 하고, 에셋 팩을 쓰면 룩이 남의 것이 된다.
- **결정**: 월드를 **빈 스케치북**으로 둔다. 바닥은 손그림 모눈종이이고, 그 위에 필요한 요소만 그린다. 마을·나무·집·소품·하늘은 두지 않는다. **스테이션은 종이 위의 그림이고, 활성화하면 3D로 전환된다.** 전환 연출은 스테이션마다 다르게 만든다(2D 유지 + 카메라 회전 / 2D→3D 애니메이션 / 3D 오브젝트가 펼쳐짐 등).
- **이유**: "그림 → 3D 전환"이 이 포트폴리오의 시그니처이고, 배경 소품은 거기에 기여하지 않는다. 배경을 비우면 소싱·모델링 비용이 사라지고 스테이션 연출에 집중할 수 있다. 남이 만든 에셋 팩에 룩이 끌려가지도 않는다.
- **영향**: DESIGN 전면 교체. PLAN 2장(아트 방향)·4장(스테이션)·로드맵 갱신. 테마는 하늘 없이 조명 색·밝기만 바뀌고(저녁 노을 정도), 네온은 후순위로 내린다.

### 009. 모눈종이 바닥: 텍스처를 스크립트로 생성 + 앱과 코드 공유

- **날짜**: 2026-07-14
- **상태**: 채택
- **맥락**: 손그림 모눈종이 텍스처가 필요한데, CC0 3D 텍스처 사이트(ambientCG·Poly Haven)에는 실사 재질만 있고 손그림 노트 종이는 없다. 직접 그리거나(A), 코드로 생성하거나(B), 무료 이미지를 받아 쓰는(C) 선택지가 있었다. 셰이더로 모눈을 직접 그리는 안은 텍스처를 쓰지 않아 폐기했다.
- **결정**: (B) **텍스처를 코드로 생성해 PNG로 굽는다.** 생성 로직과 기본값은 `src/lib/gridPaper/`에 두고, **앱과 스크립트가 같은 코드를 쓴다.** `scripts/generate-grid-paper.mjs`가 그 모듈로 PNG를 굽고(1024px), 개발용 leva HUD(`GridPaperHUD`)가 같은 모듈로 브라우저에서 즉석 미리보기를 굽는다.
- **심리스 보장**: 바닥이 타일을 수십 번 반복하므로 이음매가 없어야 한다. 선의 떨림·농담은 **타일 폭을 정수 주기로 갖는 사인파**로만 만들고, 종이 결 노이즈는 격자 인덱스를 타일 폭으로 감아 반대편과 같은 난수를 참조하게 한다.
- **칸 크기 비율 기반**: 선 굵기·떨림 폭·떨림 주기를 픽셀이 아니라 **칸 크기에 대한 비율**로 정의한다. 칸 수(`cells`)만 바꿔도 모양이 유지된다.
- **이유**: 사람이 그린 손맛에는 못 미치지만 심리스가 보장되고, 값을 즉시 조절해 눈으로 맞출 수 있다. 나중에 직접 그린 이미지로 교체해도 배선은 그대로다(PNG만 갈아끼우면 된다).
- **영향**: leva를 개발 보조 도구로 도입. 프로덕션 번들에는 들어가지 않는다(dev 전용 렌더라 트리셰이킹됨).

### 010. 바닥은 조명을 받지 않는 재질(basic)

- **날짜**: 2026-07-14
- **상태**: 채택 (임시 — 테마 구현 시 재검토)
- **맥락**: 바닥을 `MeshStandardMaterial`로 두면 화면에 찍히는 밝기가 `종이색 × 광량`이 된다. three는 물리 기반 광량이라 diffuse 반사에 1/π가 걸리고, 지금 조명값에서 광량이 1에 못 미쳐 **흰 종이가 회색(`#D4CFC8`)으로 찍혔다.** 조명을 올리면 흰색이 되지만 씬의 모든 오브젝트가 함께 밝아진다.
- **결정**: 바닥만 **조명을 받지 않는 재질**(`MeshBasicMaterial`, `toneMapped: false`)로 둔다. 지정한 종이색이 화면에 그대로 나온다. 낮/밤은 조명이 아니라 **종이색에 색을 곱해** 표현한다.
- **이유**: 종이는 흰색이어야 하고, 그것을 위해 씬 전체 조명을 왜곡할 수는 없다. 톤 매핑(ACES)도 흰색을 회색 쪽으로 눌러 이 바닥만 제외한다.
- **한계**: 바닥과 나머지 오브젝트의 밝기 체계가 이원화된다. 테마(낮/저녁/밤)를 제대로 구현할 때 다시 본다.

### 012. 콘텐츠 스키마 확정: 컬렉션별 최소 정보 원칙, 프로젝트는 Firestore 최소 필드 + 로컬 상세 확장

- **날짜**: 2026-07-16
- **상태**: 채택
- **맥락**: Phase 7에서 콘텐츠 7종(profile·skills·experiences·education·awards·spec·projects)의 실제 필드를 정하며 데이터를 입력했다. PLAN.md 초안에는 `projects` 문서 예시로 `{ title, summary, tech[], images[], links, demoKey }`가 있었으나, 이 Firebase 프로젝트는 다른 프로젝트와도 공유하는 DB라 프로젝트마다 성격이 다른 상세 필드(기술스택·이미지·데모 연결)를 여기 넣기엔 부담이 있었다.
- **결정**: `projects`는 Firestore에 `{ title, summary, startDate, endDate, link, order }`만 두고, `link`는 노션 등 외부 상세 문서로 연결한다. `tech`·`images`·`demoKey` 같은 이 포트폴리오 전용 상세 필드는 로컬에 별도 저장하며, 실제 필드는 스테이션 상세 컴포넌트를 구현하는 **Phase 8**에서 정한다. 다른 컬렉션(profile·skills·experiences·education·awards·spec)은 각각 필요한 필드만 두는 최소 원칙으로 확정했다(상세는 FIRESTORE.md).
- **이유**: Firebase 프로젝트를 여러 프로젝트가 공유하므로, 이 포트폴리오에만 필요한 상세 데이터를 Firestore 스키마에 얹으면 다른 프로젝트와의 경계가 흐려진다. 최소 정보 + 로컬 확장으로 분리하면 Firestore는 가볍게 유지되고, 상세 UI 요구사항이 정해지는 시점(Phase 8)에 맞춰 로컬 데이터 구조를 유연하게 설계할 수 있다.
- **영향**: PLAN.md 6장 프로젝트 예시 갱신. FIRESTORE.md에 컬렉션별 확정 필드 반영. Phase 8에서 로컬 프로젝트 상세 데이터 구조를 새로 설계해야 한다.

### 014. 스테이션 영역: 클릭 판정 범위 = 근접 판정 기준, 거리 계산은 스테이션에 위임

- **날짜**: 2026-07-22
- **상태**: 채택
- **맥락**: 공통층은 스테이션을 점(배치 좌표)으로만 알고, 근접은 그 점까지의 거리로, 클릭은 임시 박스 메시로 판정했다. 그런데 실제 스테이션은 종이 위에 **면적을 차지하는 그림**이다. 페이지 한가운데에서만 반응하고 가장자리에서는 반응하지 않으면 클릭도 근접도 어긋난다.
- **결정**: 스테이션마다 종이 위에 차지하는 **영역**을 두고, 그 영역이 **클릭 판정 범위이자 근접 판정 기준**이 된다. 근접은 중심점이 아니라 **영역 테두리까지의 최단거리**로 재고(영역 안이면 0), 그 계산은 형태를 아는 스테이션이 레지스트리에 `distanceTo`로 등록한다. 등록하지 않은 스테이션은 공통층이 기존대로 배치 좌표까지의 거리로 잰다.
- **클릭 처리**: 영역 전체를 덮는 투명한 판에 스테이션 id를 실어 둔다. 포인터 핸들러가 없는 메시는 R3F 이벤트 대상이 아니므로 **우클릭 이동은 그대로 바닥으로 통과**하고, 좌클릭 활성화만 `Stations`의 레이캐스트가 잡는다.
- **이유**: 스테이션마다 모양이 완전히 다르다는 원칙(006·007)을 판정에도 적용한 것이다. 공통층이 원형 반경을 강요하면 사각형 페이지든 불규칙한 오브젝트든 전부 어긋난다. 반대로 도형 종류를 데이터로 열거하면(사각형·원·…) 종류가 늘 때마다 공통층을 고쳐야 하므로, 값이 아니라 **함수**를 맡긴다.
- **영향**: `StationEntry`에 `Inactive`·`distanceTo` 추가. 영역을 등록한 스테이션에서는 `NEAR_RADIUS`가 "중심점에서"가 아니라 "영역 테두리에서 바깥으로"를 뜻하게 된다. 이 영역이 닫기 조건(근접 이탈)에도 그대로 쓰인다.

### 015. Intro 스테이션: 첫 화면을 활성 상태로 시작하고, 활성화는 카메라 각도만 바꾼다

- **날짜**: 2026-07-22
- **상태**: 채택
- **맥락**: Intro는 이름·소개·사진처럼 **읽는 내용**이 전부라 3D로 일어설 오브젝트가 없다. 또 사이트에 들어오자마자 보여야 하는 첫인상이기도 하다.
- **결정**: 내용을 **종이(바닥)에 그려 둔 채로 두고**, 활성화하면 오브젝트를 건드리지 않고 **카메라만 정면(수직)으로 돌린다.** 정면에서 보면 웹페이지처럼 읽히고, 닫으면 항공뷰로 돌아가 다시 3D 맵이 된다. 그리고 **사이트 첫 화면이 이 활성 상태**다 — 진입 애니메이션 없이 처음부터 정면뷰로 시작한다.
- **배율은 건드리지 않는다**: zoom을 바꾸면 정면에서 보이는 크기가 실제 크기와 달라져 영역 크기를 판단할 수 없다. 각도만 바꾼다.
- **화면 방향**: 수직으로 내려다보면 기본 up(+y)이 시선과 겹쳐 화면 방향이 정해지지 않는다. up을 **월드 -z로 고정**해 영역의 가로·세로가 화면의 가로·세로와 맞게 한다. 바닥에 눕힌 글씨가 바로 읽히는 방향이기도 하다.
- **복귀 자세는 계산한다**: 돌아갈 항공뷰 자세를 "지금 카메라"에서 캡처하면 안 된다. 첫 화면은 팔로우가 한 번도 돌지 않아 카메라가 캐릭터를 바라본 적조차 없고, 다시 마운트되면 이미 정면뷰인 자세를 항공뷰로 잡는다. 팔로우 규칙(`캐릭터 위치 + followOffset`, 캐릭터를 바라봄)으로 **매번 계산**한다. 걸어나가는 중에도 종료 애니메이션이 돌기 때문에 매 프레임 다시 계산해야 마지막에 튀지 않는다.
- **이유**: "종이 위의 그림이 3D로 살아난다"가 시그니처지만, 모든 스테이션이 같은 방식일 필요는 없다(007). Intro는 읽는 내용이라 각도 전환만으로 2D↔3D의 인상 차이를 만드는 편이 내용에 맞고, 첫 화면을 활성으로 두면 방문자가 조작을 배우기 전에 소개부터 읽게 된다.
- **영향**: `useStationStore` 초기값이 `about-intro`/`active`. `useCameraStore`에 `followOffset` 추가. 첫 진입에 캐릭터를 숨겼다 등장시키는 연출은 실제 캐릭터를 만드는 Phase 11로 미룬다.

### 016. 크레파스 획을 코드로 생성

- **날짜**: 2026-07-22
- **상태**: 채택
- **맥락**: 나가기 화살표를 벡터 선으로 그렸더니 자로 잰 도형처럼 보여 스케치북 톤과 맞지 않았다. 손그림 느낌의 핵심은 매끈함이 아니라 **재질감**이다.
- **결정**: 크레파스 획을 **캔버스에 코드로 그려** 텍스처로 쓴다(`src/lib/crayon/`). 크레파스는 선이 아니라 **종이 결에 걸린 왁스 알갱이 더미**라는 관점으로, 경로를 촘촘히 훑으며 굵기 안쪽에 알갱이를 흩뿌린다. 가장자리로 갈수록 찍힐 확률을 낮춰 테두리를 너덜하게 만들고, 진하기를 저주파로 흔들어 눌린 구간과 뜬 구간을 만들고, 별도 마스크로 왁스가 끊기는 구간을 둔다. 경로 자체에도 미세한 떨림을 준다.
- **씨앗 기반 난수**: 렌더할 때마다 모양이 바뀌면 안 되므로 난수에 씨앗을 준다. 획마다 씨앗을 달리해 서로 다른 손놀림처럼 보이게 한다.
- **둥근 마무리**: 끝점 바깥으로 반지름만큼 더 나가되 폭을 원의 단면으로 줄여, 잘린 단면이 아니라 반원으로 맺는다.
- **이유**: 모눈종이 텍스처를 코드로 생성한 것(009)과 같은 계열이다. 이미지 에셋을 쓰면 색·굵기를 코드로 바꿀 수 없고, 스테이션마다 손그림 요소가 계속 필요한데 그때마다 그림을 그려 넣을 수는 없다. 유틸로 두면 경로만 주면 된다.
- **영향**: `lib/Crayon` 추가. 나가기 화살표가 첫 사용처이고, 앞으로 다른 스테이션의 손그림 요소도 여기서 그린다.
- **갱신(2026-07-24)**: 경로를 손으로 박는 대신 마우스로 그려 뽑는 저작 도구를 두었다(017). 그 과정에서 획을 이어 그릴 수 있게 렌더를 증분식으로 바꾸고 획별 색을 지원한다.

### 017. 크레파스 획을 마우스로 그리는 저작 도구 + 증분 렌더

- **날짜**: 2026-07-24
- **상태**: 채택
- **맥락**: 016으로 크레파스 유틸을 두었지만, 정작 획의 경로 좌표는 코드에 손으로 박아야 했다(나가기 화살표도 `[[0.1, 0.5], …]`처럼 직접 적었다). 스테이션마다 손그림 요소가 계속 필요한데 좌표를 눈대중으로 적는 것은 번거롭고, 나중에 방문자가 바닥에 낙서하는 재미 요소로도 확장하고 싶었다.
- **결정**: 마우스로 크레파스 획을 그려 `CrayonDrawing` 좌표를 뽑는 **개발용 저작 도구**(`src/tools/CrayonStudio/`)를 둔다. 016 유틸을 그대로 쓰되, 저작 도구와 낙서 기능이 공유할 두 겹 — **획을 쌓아 두는 캔버스**(`lib/Crayon/freehand/Crayon.canvas`)와 **포인터 궤적 수집**(`lib/Crayon/freehand/Crayon.input`) — 을 나눠 둔다. 궤적을 어떤 좌표로 받을지는 쓰는 쪽이 주입한다(저작 도구는 캔버스 픽셀, 훗날 낙서는 바닥 레이캐스트).
- **증분 렌더로 전환**: 마우스로 긋는 동안 실시간으로 보이려면 늘어난 구간만 덧그려야 한다. 그런데 016은 무늬의 진행도를 **획 전체 길이 대비 비율**로 잡아, 획이 길어지면 이미 그린 앞부분 무늬까지 바뀌었다. 그래서 진행도를 **시작점부터 따라간 거리**(굵기 배수) 기준으로 바꾸고, 마지막 샘플과 끝의 둥근 마무리는 방향·위치가 정해질 때까지 보류하며, 난수 스트림을 획 단위로 이어 소비한다. 이러면 나눠 그린 결과가 한 번에 그린 것과 완전히 동일하다.
- **획별 색**: `CrayonStroke`에 선택적 `color`를 두어 한 그림에 여러 색을 섞을 수 있다. 없으면 그림이 공유하는 색을 쓴다(단색 데이터는 그대로 유효).
- **단독 페이지**: `react-router-dom`을 들여 `/`(3D 포트폴리오)와 `/crayon`(스튜디오 단독)으로 나눈다. 스튜디오는 맵 위의 모달로도, 맵 없는 단독 페이지로도 쓰며, 단독 페이지는 배포본에도 포함해 방문자가 크레파스로 그려보고 PNG로 저장할 수 있다. `그림·값 복사`처럼 코드 좌표를 뽑는 기능만 개발 모드로 가린다.
- **이유**: 좌표를 함수(도구)로 뽑으면 눈으로 맞춰 확정할 수 있고, 저작과 낙서가 같은 두 겹을 공유하므로 낙서 기능은 좌표 변환만 갈아끼우면 된다. 증분 렌더는 낙서 기능에도 그대로 필요하다.
- **영향**: `src/tools/CrayonStudio/` 추가. `lib/Crayon`에 `freehand/`(canvas·input) 신설, `Crayon.draw`가 증분 painter 위에 얹힘, `CrayonStroke.color` 추가. `react-router-dom`·`Root`·`vercel.json`(SPA rewrite) 도입. 증분 전환으로 나가기 화살표 무늬가 미세하게 달라졌으나 눈에 띄지 않아 그대로 둔다.
- **갱신(2026-07-25)**: 내보내기 프레임 도입. 점선 사각 프레임이 그림과 분리돼 내보낼 영역을 정하고(0~1 좌표 기준이자 PNG 크롭 범위), 변·모서리로 가로세로를 따로 조절한다. 프레임을 바꿔도 획은 변형되지 않는다. 기본 여백은 판 짧은 변 기준이라 직사각형 판에서도 사방이 균일하다. 클릭(점 1개)도 획 끝 둥근 마무리를 좌·우로 붙여 원형 점으로 렌더한다.

### 018. 맵 장식은 스테이션 밖 공통 자리에, 손그림 등장 연출은 `<Crayon>` 옵트인

- **날짜**: 2026-07-26
- **상태**: 채택
- **맥락**: Skills로 가는 길안내 화살표를 놓으며 두 가지가 걸렸다. 하나는 이 요소가 어느 스테이션에도 속하지 않는다는 것이다 — 영역도 근접 판정도 라이프사이클도 없이 그냥 종이 위에 놓여 있을 뿐이다. 다른 하나는 처음 등장할 때 크레파스로 긋듯 그려져야 하는데, 기존 `<Crayon>`은 완성된 그림을 한 번에 굽는다는 것이다.
- **결정**:
  - 맵 장식은 `scene/MapDecorations/`라는 **공통 마운트 자리**에 모은다. Experience는 여기 한 줄만 두고, 요소는 무엇을 언제 어떻게 그릴지 각자 정한다. Suspense도 요소마다가 아니라 이 자리에 하나만 둔다.
  - 그려지는 연출은 `<Crayon reveal={초}>` **옵트인**으로 둔다. 주지 않으면 기존과 똑같이 한 번에 굽는다.
  - 그림만의 값(획 좌표·크기·색)은 그 컴포넌트의 **하위 폴더에 `.constants.ts`로** 둔다.
- **이유**: 장식은 스테이션과 성격이 다르다. 공통층이 해줄 일이 마운트뿐이라 레지스트리(006·007)는 과하고, 그렇다고 Experience에 직접 나열하면 카메라·조명이 있는 조립 지점이 잡동사니 목록이 된다. 연출을 옵트인으로 둔 것은 매 프레임 갱신하는 텍스처가 `useLoader`(캐시·Suspense) 경로와 맞지 않기 때문이고, 상수를 컴포넌트 파일에 두지 않는 것은 스토어가 기본값을 읽을 때 순환 import가 되기 때문이다.
- **크기 배율**: 배율을 크기와 획 굵기에 함께 건다. 텍스처 픽셀 환산값이 상수로 유지돼 그림을 대각선으로 확대한 것과 같아지고, 크기를 바꿔도 다시 굽지 않아 그리던 연출이 끊기지 않는다.
- **영향**: `scene/MapDecorations/` 신설. `lib/Crayon/Crayon.reveal.ts` 추가로 `<Crayon>`이 두 갈래(한 번에 굽기·그려 나가기)로 갈린다. `SkillsGuideArrow/`·`ExitArrow/`를 하위 폴더로 분리하고 `.constants.ts`를 각자 갖는다.
- **갱신(2026-07-31) — 화살표를 실제로 옮김**: 신설 당시 안내 화살표는 Skills 폴더에 둔 채 마운트만 여기서 했고, 상태·HUD도 Skills 페이지 쪽에 얹혀 있었다. 유도 대상이 Skills일 뿐 그 스테이션에 속한 요소가 아니므로 `scene/MapDecorations/`로 옮기고 장식 전용 상태(`useMapDecorationsStore`)·HUD(`MapDecorationsHUD`)로 분리한다. 배치 좌표가 `CHARACTER_START`를 참조하던 것도 실제 값으로 고정한다 — 캐릭터 시작 위치를 옮길 때 종이에 그려진 그림이 따라갈 이유가 없다.
- **갱신(2026-07-31) — 조작 안내라는 성격 추가**: 장식에 길안내뿐 아니라 **조작 안내**도 둔다. 우클릭으로 이동한다는 것을 처음 온 사람은 알기 어려워, 오른쪽 버튼을 칠한 마우스 그림을 화살표 곁에 놓고 한 번이라도 우클릭으로 이동하면 걷는다(`useCameraStore.hasMoved`). 배운 뒤에도 남아 있으면 종이만 어지럽히므로 세션 한정으로 두고 저장하지 않는다.
- **등장 조건은 공유하고 순서는 지연으로**: 장식은 Intro가 닫힌 뒤에 나타나야 하므로 그 판정을 `useAfterIntro`로 공유한다. 다만 함께 나오면 눈이 어디를 볼지 정하지 못해, 뒤에 얹히는 것은 앞선 장식이 다 그려질 때까지 지연을 준다. 지연 값은 상수가 아니라 앞선 장식이 그어지는 시간을 그대로 쓴다.

### 019. 오려 붙인 종이 스티커를 코드로 합성

- **날짜**: 2026-07-27
- **상태**: 채택
- **맥락**: 스테이션의 비활성 모습으로 그림 파일을 쓰게 됐는데, 그대로 붙이면 종이 위에 얹힌 느낌이 없다. 이미지에 테두리·그림자를 미리 그려 넣는 방법도 있지만, 그러면 색·두께를 코드로 바꿀 수 없고 그림마다 다시 만들어야 한다.
- **결정**: 배경이 투명한 그림을 받아 **테두리와 그림자를 캔버스에서 합성해 텍스처 한 장으로 굽는다**(`lib/PaperSticker`). 실루엣을 원 둘레를 따라 겹쳐 그려 테두리 폭만큼 넓히고, 그림자는 종이를 그릴 때 함께 깔아 밑에 넣는다. 길이 값은 전부 **그림 짧은 변 대비 비율**이라 크기를 바꿔도 인상이 유지된다.
- **가장자리를 자른다**: 연필·크레파스 그림은 가장자리가 흐려서, 알파를 그대로 넓히면 테두리도 뿌옇게 번진다. 기준값으로 0/255로 잘라 실루엣을 만든 뒤 넓힌다.
- **안쪽 구멍은 메운다**: 종이는 한 장이라 **바깥 윤곽만 오리고 속은 남는다.** 그림 안쪽 틈까지 뚫려 모눈종이가 비치면 스티커가 아니라 오려낸 조각들처럼 보인다. 가장자리에서 번져 들어가 닿지 못한 곳이 곧 안쪽 구멍이다.
- **이유**: 모눈종이(009)·크레파스(016)와 같은 계열이다. 유틸로 두면 그림 파일만 갈아끼우면 되고, 앞으로 다른 스테이션의 오려 붙인 그림도 여기서 굽는다.
- **영향**: `lib/PaperSticker/` 신설. 전용 로더로 감싸 `useLoader`(Suspense)에 태우므로 텍스처 규칙(ARCHITECTURE)을 그대로 따른다. Skills의 공구함이 첫 사용처다.

### 020. Skills 활성 연출: 카메라와 오브젝트를 차례로, 전환은 비활성 구현이 소유

- **날짜**: 2026-07-27
- **상태**: 채택
- **맥락**: Skills는 Intro와 달리 종이 위에 그림(공구함)이 놓여 있다. 활성화하면 그 그림이 자리를 비켜 로고처럼 물러나고 내용이 들어설 자리가 나야 한다. 카메라 각도 전환은 Intro(015)와 같은 방식이 맞지만, 오브젝트가 함께 움직인다는 점이 다르다.
- **결정**: 카메라 각도 전환과 공구함의 로고 이동을 **겹치지 않고 차례로** 돌린다. 들어갈 때는 카메라가 먼저 돌고 그 뒤에 공구함이 물러나며, 나올 때는 공구함이 제자리로 돌아온 뒤에 카메라가 항공뷰로 돌아간다. 시간값은 공유 상수로 두고, 자기 차례가 아닌 쪽은 지연·빈 구간으로 기다린다. 라이프사이클 완료 신호는 전체 시퀀스를 아는 카메라 쪽이 낸다.
- **전환의 주인은 비활성 구현**: 로고 이동을 활성 구현(`Scene`)이 아니라 **상시 마운트된 비활성 구현이 갖는다.** 활성 구현에서 따로 그리면 같은 스티커가 두 개가 되고 전환이 끊긴다. 같은 오브젝트가 이어서 변형되는 것이 원래 모델(006·007)이다. 스토어를 구독해 gsap가 그룹만 건드리므로 매 프레임 리렌더는 없다.
- **이유**: 두 연출이 동시에 돌면 무엇이 어디로 가는지 읽히지 않는다. 순서를 두면 카메라가 자리를 잡은 뒤 그림이 물러나는 흐름이 눈에 들어온다.
- **영향**: 진입 잠금이 전체 시퀀스(2.5초) 동안 걸린다. 초점은 배치 좌표가 아니라 영역 중심(좌상단 + 반크기)에서 구해, HUD로 영역을 옮기면 함께 따라온다.
- **갱신(2026-08-03) — 캐릭터 이동이 맨 앞에 붙는다**: 진입 순서를 **캐릭터 이동 → 카메라 회전 → 공구함 로고 전환**으로 둔다. 활성화하면 캐릭터가 페이지 앞자리로 걸어가 서고, 그 뒤에 기존 두 연출이 차례로 돈다. 서는 자리는 영역 중심 기준 상대 좌표(`SKILLS_STAND`)라 영역을 옮기면 따라오고, 나갈 때 되돌리지는 않는다.
- **차례를 지연에서 신호로**: 걷는 시간은 거리에 따라 달라져 지연(delay) 상수로 차례를 맞출 수 없다. 카메라가 다 돌았음을 알리는 신호(`useSkillsSequenceStore.logoTurn`)를 활성 구현이 내고 공구함이 그것을 보고 움직인다. 전체 순서를 아는 쪽이 차례를 넘긴다는 원칙은 그대로다.

### 021. Skills 상세: 분류별 페이지 전환 + 표시 여부를 데이터로

- **날짜**: 2026-07-28
- **상태**: 채택
- **맥락**: 기술이 7개고 설명이 길어 한 화면에 다 넣으면 글씨를 읽기 힘든 크기까지 줄여야 한다. 또 내용이 아직 얕은 항목(ThreeJS)을 빼려고 코드에서 걸러내면 데이터와 화면이 어긋난다.
- **결정**: 분류로 **페이지를 나눠 넘긴다.** 제목과 로고는 고정이고 그 아래 목록만 갈린다. 열 구성은 페이지마다 정하며, 열을 하나만 적으면 그 분류를 개수로 반 나눠 두 열에 늘어놓고, 여럿 적으면 분류마다 한 열을 준다. 표시 여부는 `skills.active`로 **데이터에서** 제어하고, 필드가 없으면 표시로 다룬다.
- **이유**: 페이지를 나누면 글씨 크기를 지키면서 내용을 다 실을 수 있고, 분류가 곧 페이지라 방문자도 무엇을 보고 있는지 안다. 표시 여부를 데이터에 두면 내용을 다듬는 동안 특정 항목만 내려둘 수 있고, 코드를 고치지 않아도 된다. 없을 때 표시로 두는 것은, 문서를 추가하며 필드를 빠뜨렸을 때 화면에서 조용히 사라지는 편이 더 나쁘기 때문이다.
- **페이지 넘김**: 우측 하단에 한 번에 하나만 둔다 — 첫 페이지는 다음, 마지막은 이전. 두 페이지뿐이라 번호나 양쪽 화살표는 자리만 차지한다.
- **영향**: `SkillsPages`가 페이지 상태를 갖고 목록·페이저를 함께 쓴다. FIRESTORE의 `skills` 스키마에 `active`가 추가된다. 항목 높이는 설명이 몇 줄로 접히는지에 달려 있어, 각 항목이 배치를 끝내고 알려주는 높이로 다음 자리를 잡는다.

### 022. 나가기 요소는 공용 종이 스티커로, 자리는 스테이션이 정한다

- **날짜**: 2026-07-28
- **상태**: 채택
- **맥락**: 닫는 방법 세 가지 중 나가기 요소는 스테이션이 제공하는 몫이다(007). 그런데 스테이션마다 모양을 따로 만들면 방문자는 페이지를 옮길 때마다 나가는 곳을 다시 찾아야 한다.
- **결정**: 아이콘과 동작은 **공용으로 하나만** 둔다(`stations/ExitSticker` — 오려 붙인 종이 스티커, 누르면 `requestClose()`). 스테이션은 **놓을 자리만** 정한다. Intro의 크레파스 화살표는 그대로 두되, 이후 스테이션은 이 스티커를 쓴다.
- **이유**: "스테이션마다 다르게"는 내용과 연출에 대한 원칙이지 조작 방법에까지 적용할 것은 아니다. 닫기는 어디서나 같은 동작이므로 같은 모양이 낫다. 공용층이 자리까지 정하지 않는 것은 페이지 크기·구도가 스테이션마다 다르기 때문이다.
- **영향**: `stations/ExitSticker/` 신설. 누를 수 있는 씬 요소의 커서 처리(`stations/usePointerCursor`)도 함께 공용으로 둔다.
- **갱신(2026-08-09) — 눕는 각까지 공용이 갖는다**: 처음에는 쓰는 쪽이 눕힌 그룹(`<group rotation>`)을 만들고 그 안에 스티커를 두게 했다. 그러면 스테이션마다 눕히는 각을 다시 적어야 하고, 빠뜨리거나 다르게 적을 여지가 남아 공용으로 만든 뜻이 없다. **나가기는 어느 스테이션에서나 종이에 눕으므로** 그 각을 `ExitSticker`가 상수로 갖고 판에 직접 얹는다. 스테이션이 정하는 것은 **놓을 자리와 크기**뿐이고, 자리는 월드 좌표로 넘긴다. "자리는 스테이션이 정한다"는 원칙은 그대로다 — 값을 계산해 넘기는 주체가 여전히 스테이션이기 때문이다.

### 023. 스테이션이 서는 자리는 레지스트리 계약, 데려가는 일은 공통 함수

- **날짜**: 2026-08-03
- **상태**: 채택
- **맥락**: Skills 진입 연출을 만들며 캐릭터가 설 자리를 활성 구현이 직접 계산했다. 그런데 월드맵에서 스테이션을 고르면 같은 자리로 보내야 해서, 좌표가 스테이션 안에 묻혀 있으면 공통층이 꺼낼 수 없다.
- **결정**: 자리(`stand`, 월드 좌표)를 **레지스트리에 등록**하고, 그 자리로 **데려가는 일은 공통 함수**가 맡는다 — 걸어가면 `walkToStand`, 지도에서 고르면 `teleportToStand`. 언제 부를지(연출 순서)는 스테이션이 자기 시퀀스에서 정한다.
- **값은 스테이션 상수에**: Skills는 영역 중심(`SKILLS_CENTER`)에 오프셋(`SKILLS_STAND_OFFSET`)을 더해 상수로 만들고, Intro는 `INTRO_STAND`를 둔다. 좌표를 스토어에서 읽어 HUD로 실시간 튜닝하던 방식은 걷는다 — 확정된 값을 상수로 두고 그것을 쓰는 흐름과 어긋난다.
- **이유**: 자리는 스테이션마다 다르지만 데려가는 방법은 같다. 값은 스테이션이, 이동은 공통층이 갖는 것이 `distanceTo`를 스테이션에 맡긴 것(014)과 같은 갈래다. 반대로 이동까지 스테이션이 각자 만들면 지도에서 부를 방법이 없다.
- **배치 좌표는 선택 값**: `stations.ts`의 `position`을 선택 값으로 두고 임시로 박아 둔 좌표를 지운다. 자리가 정해진 스테이션만 종이 위와 지도에 나오고, 나머지는 상세 구현에서 영역과 함께 정한다. 정해지지 않은 자리를 임시 좌표로 채워 두면 지도에 있지도 않은 것이 놓인다.
- **영향**: `StationEntry`에 `stand` 추가. 씬 배치·근접 판정·미니맵·월드맵이 자리 없는 스테이션을 건너뛴다. 월드맵에서 고른 스테이션은 좌표만 옮기고 활성화하지 않는다.
- **갱신(2026-08-07) — 자리를 함수로도 등록**: `stand`에 값뿐 아니라 **함수**도 등록할 수 있다. 자리가 늘 같은 점인 스테이션(Intro·Skills)은 값 그대로 두고, 캐릭터가 선 자리에 따라 달라지는 스테이션은 함수를 둔다. Career는 어느 쪽에서 오든 **가장 가까운 영역 테두리**로 가야 해서, 한 점으로 박아 두면 위에서 눌러도 멀리 돌아간다. 거리 계산을 스테이션에 맡긴 것(014)과 같은 갈래로, 값이 아니라 함수를 맡기면 공통층은 여전히 "데려가는 일"만 한다. 자리를 푸는 시점은 부르는 순간이라 월드맵 순간이동도 그때 위치를 기준으로 삼는다.
- **갱신(2026-08-04) — 데려가는 방법이 둘**: 자리로 보내는 함수를 `walkToStand`(연출 이동)와 `moveToStand`(평소 이동)로 나눈다. 스테이션이 아직 카메라를 쥐고 있는 동안(종료 애니메이션 중)에 연출 이동으로 보내면, "연출 이동 중에는 평소처럼 따라간다"는 규칙(007 갱신)에 걸려 팔로우가 되살아나 복귀 트윈과 부딪힌다. 그때는 평소 이동으로 보내고 카메라를 돌려받은 뒤에 연출 이동으로 바꾼다. `walkToStand`는 자리를 등록하지 않았으면 false를 준다 — 도착을 기다리는 쪽이 영영 기다리지 않도록.

### 024. 면을 채운 크레파스 그림의 바깥 윤곽 마무리

- **날짜**: 2026-08-04
- **상태**: 채택
- **맥락**: 크레파스 획은 `roughness`로 **획 한 줄의 좌우 가장자리**를 너덜하게 만든다. 그런데 획을 겹쳐 면을 채우면 겹친 안쪽이 꽉 차면서 **그림 전체의 바깥 윤곽만 딱 떨어진다.** 횡단보도처럼 바닥을 메운 그림에서 이 잘린 자국이 그대로 드러났다.
- **결정**: 그림이 채울 영역을 **그리기 전에 한 장 만들어 두고**, 알갱이를 찍을 때 그 자리가 얼마나 안쪽인지 보고 바깥일수록 건너뛴다(`lib/Crayon/Crayon.edge.ts`). 옵트인이라 값을 주지 않으면 난수를 소비하지도 않아 기존 사용처(나가기 화살표·길안내 화살표)의 그림이 완전히 같다.
- **후처리가 아니라 그리기 단계에서**: 다 그린 캔버스를 깎는 방식은 그려 나가는 연출(`reveal`)과 맞지 않는다. 매 프레임 후처리를 돌리면 비싸고, 끝나고 한 번만 걸면 다 그은 순간 경계가 정돈되는 것이 보인다. 값밭을 미리 만들어 두면 첫 획부터 테두리가 적용된 채로 그어진다.
- **모서리는 각지게**: 안쪽인 정도를 사방으로 퍼지는 흐림 한 번으로 재면 모서리에서 두 변이 함께 깎여 **직각이 둥글어진다.** 가로·세로를 따로 재 **낮은 쪽**을 쓰면 등고선이 사각이라 각지게 남는다. 두 값을 곱하면 사방으로 흐린 것과 같아지므로, 그 사이를 오가는 값(`roundness`)을 둔다.
- **판 테두리도 경계로 다룬다**: 획이 판 밖까지 나간 그림은 거기서 잘리므로, 그 잘린 자국도 함께 마무리돼야 자연스럽게 끝난다.
- **이유**: 앞으로도 면을 채운 손그림이 계속 나온다. 그림마다 가장자리를 손보는 대신 값 두 개(`feather`·`strength`)로 조절하게 두면 크레파스 유틸을 쓰는 어느 그림에나 그대로 적용된다.
- **한계**: `roundness`는 값만 있고 눈에 띄는 차이를 만들지 못한다. 지금은 각진 쪽으로 두고 쓴다.
- **영향**: `lib/Crayon`에 `Crayon.edge.ts` 신설, `CrayonSharedParams`에 `edge` 추가. 굽는 쪽과 그려 나가는 쪽이 같은 값밭을 나눠 쓴다.

### 025. 종이 스티커는 컴포넌트로만 쓴다

- **날짜**: 2026-08-04
- **상태**: 채택
- **맥락**: `lib/PaperSticker`가 굽는 훅(`usePaperStickerTexture`)과 컴포넌트(`<PaperSticker>`)를 함께 내보내고 있었다. 재질을 바꿔야 하는 쓰임(스티커를 겹쳐 놓기·바닥 그림자)에서는 컴포넌트가 재질을 고정으로 그려 쓸 수 없었고, 그때마다 훅을 꺼내 판을 직접 만들었다. 같은 코드가 여러 곳에 흩어졌다.
- **결정**: **배럴에서 굽는 훅을 뺀다.** 밖에서 텍스처를 꺼낼 방법이 없으니 스티커를 그리는 일은 전부 `<PaperSticker>`를 지난다. 대신 컴포넌트가 그만큼 넓어진다 — 재질(`color`·`opacity`·`depthWrite`)과 같은 스티커를 여러 장 늘어놓기(`count`·`gap`)를 props로 받는다. 미리 굽기(`preloadPaperSticker`)는 분해가 아니라 캐시를 채우는 일이라 남긴다.
- **이유**: 컴포넌트는 재사용하려고 만드는 것이지 분해해서 쓰라고 만드는 것이 아니다. 훅이 열려 있으면 "조금 다른 쓰임"마다 판을 새로 만들게 되고, 판 크기 계산·색공간·투명 처리가 그때마다 복제된다.
- **영향**: `ExitSticker`·`SkillLevel`이 판을 직접 만들던 코드를 걷었다. 별을 늘어놓는 규칙(그림 폭 기준 간격·겹치므로 깊이 끄기)이 컴포넌트 안으로 들어가 쓰는 쪽은 개수와 간격만 준다. 세워 두는 스티커와 그 바닥 그림자도 같은 컴포넌트로 그린다.
- **갱신(2026-08-07) — 잰 크기는 알려준다**: 굽는 훅을 닫아 둔 대신 `onMeasure`를 열어, 구운 그림의 월드 가로·세로를 쓰는 쪽에 알린다. 가로는 그림 비율에서 나오므로 굽기 전에는 알 수 없고, 그것을 모르면 그림마다 폭이 다른 로고를 왼쪽 정렬하거나 제목을 오른쪽 끝에 붙일 수 없다. 텍스처를 밖으로 꺼내는 것이 아니라 결과 크기만 알리는 것이라 "컴포넌트로만 그린다"는 원칙은 그대로다.

### 026. Career 활성 연출: 테두리로 데려간 뒤 카메라와 로고를 동시에

- **날짜**: 2026-08-07
- **상태**: 채택
- **맥락**: Career는 종이 두 장과 트로피가 놓인 스테이션이라, 활성화하면 셋이 물러나고 그 자리에 내용이 들어서야 한다. Skills(020)는 카메라와 오브젝트를 **차례로** 돌렸는데, 여기는 물러날 것이 셋이라 하나씩 차례를 주면 전환이 길어진다.
- **결정**: 진입 순서를 **캐릭터 이동 → (카메라 회전 + 로고 전환)** 으로 둔다. 캐릭터가 자리에 선 뒤에는 카메라와 세 그림이 **같은 시간·이징으로 함께** 움직인다. 나올 때도 함께 되돌아간다.
- **서는 자리는 가장 가까운 테두리**: 한 점으로 박아 두면 어느 쪽에서 눌러도 그리로 돌아가야 한다. 캐릭터 위치를 영역 사각형에 가둬 나온 지점(위에서 오면 위 테두리, 왼쪽에서 오면 왼쪽 테두리)으로 데려간다. **영역 안에서 열면 이동을 건너뛴다** — 이미 페이지 위에 서 있는데 테두리로 도로 나가는 것은 어색하다. (023 갱신)
- **로고는 공통 높이로**: 영역을 셋으로 나눠 각 칸 왼쪽에 붙이는데, 배율로 줄이면 평소 크기가 다른 셋이 제각각 크기로 앉는다. 배율이 아니라 **로고 높이**를 정해 각자 그 높이에 맞춰 줄어들게 한다. 간격도 로고 중심이 아니라 **잰 그림 가로** 기준이라 폭이 달라도 제목까지의 거리가 같다. (025 갱신)
- **트로피는 눕힌다**: 정면뷰는 수직으로 내려다보는 시선이라 세워 두면 위통수만 보인다. 물러나면서 눕혀 정면이 화면을 보게 하고, 그동안 바닥 그림자는 걷는다. 누운 그림에는 선 그림자가 뜻이 없다.
- **이유**: 셋이 각자 차례를 기다리면 전환이 늘어지고, 무엇이 어디로 가는지도 이미 카메라가 도는 동안 눈에 들어온다. 차례를 지연 상수가 아니라 신호(`useCareerSequenceStore`)로 넘기는 것은 걷는 시간이 거리마다 다르기 때문이다(020과 같은 이유).
- **영향**: `stand`가 함수를 받게 되고(023), `<PaperSticker>`가 잰 크기를 알린다(025). 전환의 주인은 Skills와 같이 **상시 마운트된 비활성 구현**이다 — 활성 쪽에서 따로 그리면 그림이 두 개가 되고 전환이 끊긴다.

### 027. 부품이 여럿인 모델의 바닥 그림자는 스텐실로 한 겹만 칠한다

- **날짜**: 2026-08-07
- **상태**: 채택
- **맥락**: 세워 둔 것이 바닥에 붙어 보이려면 그림자가 필요하다(신호등, DESIGN). 신호등은 판 한 장이라 같은 그림을 검게 눌러 눕히면 됐지만, 트로피는 몸체·손잡이·받침이 각각 면을 이룬 3D 모델이라 같은 방법이 통하지 않는다. 반투명하게 눕히면 **겹친 곳만 진해져** 그림자가 여러 조각으로 보인다.
- **거쳐 간 방법**: 깊이로 한 번만 통과시키기(부품마다 깊이가 미세하게 달라 실패), 더 어두운 쪽만 남기는 블렌딩(겹침은 사라지지만 밑의 모눈종이를 덮어버림).
- **결정**: 실루엣을 **스텐실 버퍼에 표시**해 두고, 표시된 자리에만 판 하나를 **한 겹** 칠한다. 몇 겹이 겹치든 칠은 한 번이라 진하기가 고르고, 평범한 알파 블렌딩이라 밑의 모눈이 그대로 비친다. 이를 위해 Canvas에서 스텐실 버퍼를 켠다(three 기본값은 꺼짐).
- **실루엣은 위에서 눌러 만든다**: 모델을 옆으로 눕히면 깊이 방향으로 뻗은 손잡이가 몸체 뒤에 가려 사라진다. 높이가 곧 눕는 거리가 되는 **전단 변환**으로 위에서 내려다본 모습을 바닥에 눕히면, 옆으로 뻗은 것도 그대로 남고 방향·길이도 그 변환의 값으로 조절된다.
- **이유**: 그림자는 한 덩어리로 보여야 그림자다. 앞으로도 3D 모델을 세워 두는 스테이션이 나오므로, 그림마다 손보는 대신 같은 방식으로 처리한다.
- **영향**: `Experience`의 Canvas에 `stencil: true`. 스텐실 값을 상수로 하나 잡아 두었으므로, 다른 곳에서 스텐실을 쓰게 되면 값을 나눠야 한다.

### 028. Career 상세: 칸마다 다른 데이터를 한 형태로 맞춰 같은 항목으로 그린다

- **날짜**: 2026-08-09
- **상태**: 채택
- **맥락**: Career는 칸이 셋(교육 · 수상내역 · 자격증)이고 각각 다른 컬렉션을 읽는다. `education`은 과정명·기간·기관, `awards`는 수상명·설명·시기·기관, `spec`은 자격증명·취득일·발행처로 필드가 제각각이다. 칸마다 전용 컴포넌트를 두면 같은 배치·측정 코드가 세 벌이 되고, 한 컴포넌트에서 분기하면 컬렉션이 늘 때마다 분기가 쌓인다.
- **결정**: 화면에 필요한 모양을 먼저 정하고 **그리기 전에 그 한 형태로 정규화**한다(`CareerColumns.data`). 형태는 `{ 제목, 제목 아래 본문 줄, 맨 아래 좌/우 한 줄 }`이고, 그리는 쪽(`CareerEntry`)은 이 한 종류만 다룬다. 칸이 늘거나 컬렉션이 바뀌면 변환 함수만 더한다.
- **좌/우 한 줄**: 제목 아래에 왼쪽 기간 · 오른쪽 기관명을 두고 **오른쪽 값은 칸 오른쪽 끝에 건다**. 왼쪽 글 길이가 제각각이어도 오른쪽 줄이 가지런히 맞는다. 자격증도 같은 모양이라 세 칸이 한 규칙으로 읽힌다.
- **본문은 인용 막대로**: 수상 설명은 줄마다 기호(`-`)를 붙이지 않고 Intro 소개글처럼 왼쪽에 세로 막대를 세운다. 여러 줄이어도 **한 인용 블록 안에서 줄만 나뉘어** 항목이 여럿으로 보이지 않는다. 막대 높이는 접힌 본문 높이를 따라간다.
- **높이는 재는 것과 세는 것을 나눈다**: 본문이 몇 줄로 접힐지는 미리 알 수 없어 troika가 배치를 끝낸 뒤 주는 값으로 잰다. 본문이 없는 교육·자격증은 글자 크기와 줄 수로 바로 계산돼 **측정을 기다리지 않는다**. Firestore 읽기와 측정은 `useStationGate`로 잡아 뒀다가 다 되면 한 번에 보여준다.
- **이유**: 스테이션마다 다르게 만든다는 원칙(006·007)은 스테이션 사이의 이야기이고, 한 스테이션 안에서 성격이 같은 것을 세 벌로 만들 이유는 없다. 데이터 모양의 차이를 화면 앞이 아니라 데이터 쪽에서 흡수하면 그리는 코드가 단순해진다.
- **영향**: `CareerColumns/`(목록·정규화·항목)·`CareerExit/` 신설. Skills가 분류별 페이지로 넘긴 것(021)과 달리 Career는 건수가 적어 페이지를 나누지 않는다. 정렬은 전부 최신순이고 기간 표기(`2023.01 ~ 2023.12`, 진행 중이면 `~ 현재`)도 변환 쪽에 모아 둔다.

### 029. 영역 여백은 공용 개념, UI 요소는 여백을 따르지 않는다

- **날짜**: 2026-08-09
- **상태**: 채택
- **맥락**: 스테이션 영역은 클릭·근접 판정 범위라(014) 읽을 내용보다 넓게 잡힌다. 그래서 내용을 영역 테두리에 딱 붙이면 답답하고, 나가기 아이콘이 놓인 구석에는 글이 그 밑으로 들어간다. 처음에는 나가기 몫으로 열을 하나 더 두어 4열로 나눴는데, 내용 칸이 셋인데 열이 넷이라 분할이 어긋나고 내용이 화면 가운데에서 밀렸다.
- **결정**: 영역에 **여백**(`StationAreaPadding` — 좌우 `x` · 상하 `y`)을 두고, 그것이 내용이 놓일 안쪽 상자를 정한다. 칸 분할·로고·제목·목록·구분선이 모두 이 안쪽을 기준으로 놓인다. 좌우가 같은 폭이라 내용이 화면 가운데 놓이고, 오른쪽 여백이 나가기 자리를 비워 준다. 타입을 `stations/types`에 공용으로 둬 **새로 만드는 영역은 크기·좌표와 함께 이 여백을 기본으로 갖는다.**
- **UI 요소는 예외**: 나가기·페이지 넘김처럼 구석에 붙는 조작 요소는 이 여백을 따르지 않고 **영역 테두리에서 바로 잰다.** 여백을 넓히면 읽을 내용만 물러나고 조작 요소는 그 자리에 남아야 한다. 여백을 따르게 하면 여백을 키울수록 X가 화면 안쪽으로 파고든다.
- **이유**: 나가기 자리를 만들려고 열을 더 두는 것은 그 자리 하나를 위해 **분할 규칙 전체를 비트는** 일이다. 여백은 그 자체로 여백이고, 내용 칸은 칸 수대로 고르게 나뉜다. 여백을 공용 타입으로 둔 것은 영역이 있는 스테이션이면 어디나 같은 문제를 만나기 때문이다.
- **영향**: `stations/types`에 `StationAreaPadding` 추가. Career에 적용하고 HUD `영역` 폴더가 가로·세로 크기, 테두리 표시, 좌표, 상하·좌우 여백을 모두 갖는다. 이미 만든 Intro·Skills는 각자의 방식(내용별 여백)으로 두고 손대지 않는다 — 화면이 이미 맞춰져 있어 기준을 바꾸면 값을 다시 잡아야 한다.

### 030. 에셋 출처는 화면에, 폰트 라이선스는 파일 옆에

- **날짜**: 2026-08-10
- **상태**: 채택
- **맥락**: 트로피에 이어 자동차 모델을 Poly Pizza에서 가져오며 출처를 어디에 밝힐지 정해야 했다. 콘솔 로그나 레포 문서에 남기는 안도 있었다. 폰트도 self-host라 같은 문제를 안고 있는데, 두 라이선스가 요구하는 방식이 서로 다르다.
- **결정**: 요구하는 방식에 맞춰 자리를 나눈다.
  - **3D 모델(CC-BY)은 화면에** — 구석 버튼과 모달(`ui/Credits`), 목록은 `content/credits.ts`.
  - **폰트(OFL)는 파일 옆에** — `public/fonts/*/OFL.txt`. 화면 표기는 두지 않는다.
  - **레포에 `LICENSE`** — 코드만 MIT이고 그림·사진·3D 에셋과 이력서 내용은 제외한다.
  - **npm 의존성은 다루지 않는다.**
- **이유**: CC-BY는 "매체에 합당한 방식"의 표기를 요구하므로 방문자가 볼 수 있는 곳이라야 한다. 콘솔이나 주석은 개발자 도구를 여는 사람만 보므로 표시했다고 보기 어렵고, 취업용 포트폴리오에서 숨겨 둔 크레딧은 지키지 않으려 한 흔적으로 읽힌다. 반대로 OFL은 화면 표기를 요구하지 않고 **재배포할 때 라이선스 전문이 폰트 파일과 함께 갈 것**을 요구하므로, 폰트를 크레딧 모달에 싣는 것은 의무가 아니다. 하나의 "저작권 표기"로 묶지 않고 각자가 요구하는 자리에 둔다.
- **실물을 함께 보여준다**: 목록만 두지 않고 고른 에셋을 모달 안 별도 캔버스에 띄운다. 어떤 모델을 어디에 쓰고 있는지가 이름만으로는 읽히지 않는다. 모델마다 크기·원점이 달라 경계 상자를 재 **가장 긴 변을 1로 맞추고 중심을 원점에** 두면, 카메라를 고정한 채 무엇이든 담기고 거리 제한값이 모델과 무관하게 같은 뜻을 갖는다.
- **Pretendard 서브셋의 예약 이름은 알면서 그대로 둔다**: OFL은 글자 모양이 아니라 파일 구성을 기준으로 개작본을 정의하므로(`deleting ... in part`·`changing formats`), 자형을 건드리지 않은 서브셋도 Modified Version이다. OFL FAQ도 웹폰트용 서브셋을 개작으로 못박고 있고, 거기 있는 좁은 예외("완전한 기능적 동등성")는 글리프를 덜어낸 이 서브셋에 해당하지 않는다. Pretendard는 Reserved Font Name을 선언하고 있으며 서브셋 ttf의 이름표에 그 이름이 그대로 남아 있다(Gamja Flower는 RFN이 없어 무관). **규정대로라면 이름을 바꾸거나 서면 허락을 받는 것이 맞다.** 그럼에도 두는 근거는 3조의 제한이 **"사용자에게 제시되는 주 폰트 이름"** 에만 걸린다는 단서다. 이 파일은 troika가 3D 글자를 그리려고 직접 읽을 뿐 설치되지도 폰트 목록에 뜨지도 않는다. 다만 `public/`에 있어 파일 자체는 배포되고 그 안의 이름표도 함께 나가므로, 이 근거는 해석에 기대고 있다. 재배포 고지 의무는 `OFL.txt`로 지킨다.
- **영향**: `ui/Credits/`·`ui/CornerButton/`·`content/credits.ts` 신설. 크레파스 버튼의 스타일이 `CornerButton`으로 옮겨 가 두 버튼이 자리를 나눠 쓴다. 에셋을 새로 가져오면 `credits.ts`에 한 줄 넣는다. Pretendard 이름 판단은 근거가 해석에 기대고 있으므로, 폰트 파일 자체를 배포물로 내세우게 되면 다시 본다.

### 034. 프로젝트 실내는 별도 라우트·별도 Canvas로 두고 덮개로 잇는다

- **맥락**: 건물 문으로 들어가면 실내가 나와야 한다. 맵과 같은 씬에 방을 짓고 카메라만 옮기는 안, 같은 라우트에서 Canvas 내용만 갈아 끼우는 안, 라우트를 따로 두는 안이 있었다. 실내는 맵과 세계가 통째로 다르다 — 밟는 바닥도, 막는 것도, 카메라 규칙도, 심지어 투영 방식도 같지 않다.

- **오가는 사이는 덮개가 맡는다**: 라우트가 갈리면 Canvas가 통째로 새로 서고 모델을 받는 동안 화면이 빈다. 원형으로 조여드는 덮개(`ui/SceneTransition`)를 **라우트 바깥**에 두어, 다 덮인 뒤에 주소를 바꾸고 새 장면이 **도착 신호**(`scene/SceneArrival`)를 보내면 연다. 덮개가 조여드는 중심은 문 자리라, 문으로 빨려 들어가고 문에서 나오는 것으로 읽힌다.
- **이유**: 한 씬에 다 넣으면 "지금 어디에 있나"를 코드 곳곳에서 갈라야 한다 — 클릭 판정, 카메라 리그, 이동 한계, 미니맵까지 전부 조건문이 붙는다. 라우트로 가르면 그 조건이 라우팅 한 곳으로 모이고, 실내가 무거워져도 맵의 첫 로딩에 얹히지 않는다. 대신 **두 장면이 서로를 모른다**는 대가가 있어, 오가며 정리할 것(스테이션 닫기·문 앞에 세우기)을 `ProjectsLobby.travel.ts` 한자리에 모은다.
- **뒤로가기도 대비한다**: 브라우저 뒤로가기는 주소만 되돌리고 앱 상태는 건드리지 않아, 그대로 두면 맵이 뜨자마자 스테이션이 열려 진입 연출이 다시 돈다. 맵이 뜰 때 실내 흔적을 걷는다(`ensureOutsideBuilding`).
- **영향**: `stations/sections/projects/ProjectsLobby/` 신설, `Root`에 라우트와 덮개, `useSceneTransitionStore`·`useLobbyStore` 등 실내 전용 스토어. 맵 쪽은 첫 카메라 자리를 캐릭터 기준으로 잡아 돌아왔을 때 튀지 않게 하고, 첫 화면 게이트는 진짜 첫 방문에만 뜬다.
- **2026-08-22 갱신 — 조여드는 원의 시작 지름을 바로잡는다**: 시작 지름을 화면 대각선의 두 배처럼 넉넉히 잡으면, 그 크기가 이미 화면 밖이라 조여드는 시간의 앞쪽 절반은 줄어도 눈에 아무 변화가 없다. 초점 기준으로 **화면을 꼭 덮는 최소 지름**을 매 프레임 계산해 쓰면 시작 신호와 보이는 변화가 바로 맞는다. 초점이 매 프레임 바뀌는 것(문·통로 자리)도 그대로 따라간다.
- **2026-08-22 갱신 — `useLobbyStore`를 `useInteriorStore`로 통합**: 전시 공간이 로비와 같은 실내 규칙(우클릭 홀드 이동·고정 속도)을 쓰게 되면서, 방마다 따로 두던 이동 스토어를 하나로 합치고 시작 자리를 `reset` 인자로 받는다. 라우트로 갈려 두 방이 동시에 뜨지 않으므로 하나의 스토어를 돌려써도 섞이지 않는다.

### 035. 실내의 룩은 등이 아니라 환경광이 만든다

- **날짜**: 2026-08-20
- **상태**: 채택
- **맥락**: 실내를 붙였더니 금속 손잡이와 벽등이 새까맣고, 흰 대리석은 반대로 하얗게 타 계조가 없었다. 등을 늘려도 금속은 그대로 검었다.
- **결정**: 실내의 기본 밝기는 **환경(IBL)** 이 만들고, 등은 그 위에 웅덩이를 얹는 역할만 한다. 밝기 잘림은 노출로 화면 안에 들인다.
- **손잡이가 하나로 묶이는 것을 가른다**: 환경광 세기를 낮추면 금속이 어두워지지만 광택까지 죽는다. 어둡게 두고 싶은 재질에 **자기 환경맵을 따로 물리면** 씬 환경광 세기를 타지 않아, 반사(광택)는 남기고 밝기만 뺄 수 있다.
- **등은 벽에서 떼어 놓는다**: 모델의 광원이 벽면에 거의 파묻혀 있어 빛 웅덩이가 얇은 띠가 됐다. 방 안쪽으로 밀어 둥글게 퍼지게 한다.
- **그림자는 한 번 굽고 얼린다**: 방도 등도 움직이지 않으므로 매 프레임 다시 그릴 이유가 없다. 다만 **얼려도 읽는 비용은 남는다** — 그림자를 켠 등 하나가 모든 재질의 셰이더에 큐브맵 훑기를 한 겹 더하므로, 켜는 등의 개수를 정해 놓고 쓴다.
- **이유**: 오프라인 렌더는 간접광이 알아서 채워 주지만 실시간에는 그 몫을 환경맵이 대신한다. 등을 늘려 밝기를 맞추는 것은 비용이 개수만큼 붙는 데다, 확산광이 없는 금속에는 애초에 듣지 않는다.
- **영향**: `LobbyEnvironment` 신설, 재질·조명 값은 `ProjectsLobby.constants`에 모은다. **반구광과 노출은 재질별로 나눌 수 없어** 대리석을 맞추면 금속이 밝아지는 상충이 남는다 — 지금은 대리석 쪽을 기준으로 잡았다.

- **맥락**: 실내 콜라이더를 축 정렬 경계 상자로 재서 막았더니, 계단을 따라 **기울여 놓은 난간**이 기울기를 다 감싸는 직육면체가 되어 계단 위를 침범했다. 열린 바닥인데도 벽에 부딪히듯 옆으로 미끄러졌다.
- **결정**: 콜라이더 메시에서 **바깥을 향한 면(평면)들을 뽑아** "모든 면의 안쪽인가"로 판정한다. 겹쳤으면 가장 얕게 빠져나오는 면 쪽으로 **수평으로만** 민다.
- **감는 방향을 믿지 않는다**: 거울로 복제한 메시는 면이 뒤집혀 법선이 안쪽을 향하고, 그러면 어디에 있든 "밖"으로 읽혀 한 번도 막지 못한다. 볼록체는 정점 평균이 반드시 안쪽이므로 그 점으로 뒤집힌 면을 바로잡는다.
- **캐릭터는 기둥으로 친다**: 점이 아니라 반지름과 높이를 가진 기둥이라, 면을 그 두께만큼 바깥으로 밀어 두고 점 하나로 검사한다. 발밑 얼마간은 판정에서 빼 문턱·바닥 콜라이더에 걸리지 않게 한다.
- **모델에 없는 면은 늘려서 메운다**: 계단 옆면 콜라이더가 모델에 빠져 있었다. 새 상자를 세우면 방금 고친 문제(기울기를 죽인 축 정렬 상자)를 그 자리에 다시 만드는 셈이라, **난간의 면을 아래로 내려** 기울기를 그대로 물려받게 한다.
- **이유**: 방은 기울어진 것투성이(난간·경사)라 축 정렬 상자로는 형태가 살지 않는다. 볼록 판정은 평면 개수만큼의 내적이면 끝나 비용도 상자와 크게 다르지 않다. **대신 볼록한 것만 다룬다** — 오목한 형태는 상자 여럿으로 쪼개 놓아야 한다.
- **영향**: `ProjectsLobby.collision.ts` 신설. 콜라이더는 이름 규칙(`Collider_*`)으로 모으고, 아래로 늘릴 것은 상수로 지정한다. 눈으로 확인할 개발용 보기(단색)를 함께 둔다.
- **2026-08-22 갱신 — 정면 충돌에 미끄러지도록 앞을 뾰족하게 깎는다**: 축에 나란한 콜라이더는 정면으로 부딪히면 어느 쪽으로도 밀리지 않는다. 밀어내기가 빠져나가는 데 가장 덜 움직이는 면을 고르는데, 정면에서는 축에 나란한 앞면이 늘 가장 얕아 걸음과 정반대로 되밀려 그 자리에 멎기 때문이다. **앞면을 걷어내고 비대칭 경사면 두 장으로 갈아 끼워** 오각형으로 만들면, 부딪히는 순간 한쪽으로 미끄러진다. 꼭짓점을 가운데서 비켜 두는 것이 핵심이다 — 대칭이면 정면으로 마주 선 캐릭터가 어느 쪽으로도 밀리지 못한다. 통로 길목의 연단에 적용했다.
- **2026-08-24 갱신 — 한 메시에 든 볼록체 여럿은 갈라서 각자 만든다**: 문이 뚫린 벽은 볼록하지 않은데 콜라이더가 메시 하나다. 그대로 읽으면 정점 평균이 **문 구멍**에 떨어지고, 그 점을 안쪽으로 삼아 면을 뒤집으면 남는 볼록체가 벽이 아니라 문 구멍이 된다. 벽은 통과되고 지나갈 곳이 막힌다. 콜라이더를 덩어리로 갈라 덩어리마다 볼록체 하나씩 만들면 "볼록한 것만 다룬다"를 지키면서 오목한 벽도 다룰 수 있다. **가르는 기준은 정점이 아니라 모서리다** — 맞닿은 상자는 꼭짓점이 겹쳐 정점으로 잇는 `lib/geometryIslands`로는 한 덩어리가 된다. 상자 하나 안의 모서리는 삼각형 둘이 쓰고 맞닿은 자리의 모서리는 넷이 쓰므로, 둘만 쓰는 모서리로만 이으면 갈린다. 전시 공간에만 적용한다(`GalleryModel.blockers.ts`).

### 037. 실내 카메라는 제한된 기준점을 따라가고, 트리거를 열면 한 진행도로 섞는다

- **날짜**: 2026-08-20
- **상태**: 채택
- **맥락**: 맵처럼 카메라가 캐릭터를 그대로 따라가니 방이 통째로 흔들려 실내로 읽히지 않았다. 특히 좌우로 걸을 때마다 벽이 밀려 다녔다.
- **결정**: 카메라가 보는 **기준점을 제한**한다. 좌우는 시작 자리에서 정해진 폭만큼만 따라가고, 앞뒤는 **계단 중턱까지는 고정**했다가 그 뒤로 오른 만큼의 절반만 따라간다. 방을 관객석에서 보는 그림이 유지되고, 2층으로 오르면 시야가 따라 올라온다.
- **트리거를 열면 같은 카메라를 섞는다**: 책을 누르면 카메라를 따로 만들지 않고 **0→1 진행도 하나**로 기준점·오프셋·비켜 놓기를 한꺼번에 목표 값으로 보간한다. 되돌리는 것은 진행도를 되돌리는 것뿐이다.
- **자세를 다 잡은 뒤 행렬을 마무리한다**: `lookAt`이 내부에서 월드 행렬을 굳혀, 그 뒤의 비켜 놓기가 행렬에 안 들어간다. 같은 프레임에 카메라를 읽는 조준(레이캐스트)이 옛 자리를 보게 되므로 마지막에 한 번 갱신한다.
- **이유**: 실내는 벽이 화면 끝을 잡아 주는 그림이라 카메라가 자유로우면 그 틀이 깨진다. 트리거마다 카메라를 새로 두면 돌아오는 길을 각자 구현해야 하고, 도중에 다른 것을 누르면 서로 싸운다.
- **영향**: `LobbyCameraRig`가 이동·포커스를 함께 맡는다. 제한 값과 포커스 목표는 상수로 두고 개발용 HUD로 맞춘다.

### 038. 책 글씨는 캔버스 텍스처로, 글 쓰는 면에만 얹는다

- **날짜**: 2026-08-20
- **상태**: 채택
- **맥락**: 연단 위 펼친 책에 글을 써야 하는데, 책은 종이가 휘어 있다. 3D 글자(troika)를 띄우는 안은 곡면을 따라가지 못해 글씨가 종이에서 떠 보인다.
- **결정**: 페이지 넓이만 한 **캔버스에 그려 텍스처로 얹는다.** 종이의 UV를 그대로 타므로 휜 모양을 따라 글씨도 휜다. 진짜 인쇄물처럼 읽힌다.
- **글 쓰는 면만 가른다**: 페이지 메시에는 종이 두께(옆면)와 책등 띠가 함께 있어 그대로 얹으면 옆면에도 글씨가 흐른다. **면이 위를 향하는가**와 **책등 쪽 띠에 드는가**로 삼각형을 갈라 지오메트리 그룹 둘로 만들고, 글 쓰는 쪽에만 텍스처 재질을 준다. 메시를 복제하지 않아 겹쳐 깜빡이지 않는다.
- **좌우는 따로**: 한 장의 텍스처를 두 페이지가 나눠 쓰면 가운데가 겹쳐 나온다. 메시 이름으로 좌·우를 나눠 캔버스를 둘 만든다.
- **바탕은 흰색으로 채운다**: 투명 바탕에 글씨만 얹으면 종이색이 남는 게 아니라 **뚫린다.** 텍스처는 재질 색에 곱해지므로 흰 바탕이 곧 원래 종이색이다.
- **이유**: 책은 방문자가 가장 먼저 읽는 안내판이라 글이 종이에 붙어 있어야 한다. 캔버스는 줄바꿈·정렬·글꼴을 2D 그리기로 다룰 수 있어, 오른쪽 페이지에 Firestore `projects`를 순서대로 흘려 넣기에도 맞다.
- **영향**: `ProjectsLobby/LobbyBook/` 폴더에 상수·면 가르기·그리기·내용·텍스처를 모은다. 캔버스 글씨는 **글꼴을 먼저 받아야** 하고(한글은 범위별 서브셋이라 그릴 글자를 함께 넘긴다), glTF의 UV 원점이 위쪽이라 `flipY`를 끈다. 캔버스 비율은 페이지 실측이 아니라 눈으로 맞춘 값이라 여백이 완전히 고르지는 않다.

### 039. Draco 디코더는 self-host하고 결과물을 커밋한다

- **날짜**: 2026-08-20
- **상태**: 채택
- **맥락**: 로비 모델이 커서 Draco로 압축했는데, 기본 디코더 경로가 외부 CDN(gstatic)이다. DESIGN의 "외부 CDN 요청 없음"과 어긋나고, 그 도메인이 막히면 모델이 통째로 안 뜬다.
- **결정**: 디코더를 `public/draco/`에 두고 로더가 그곳을 보게 한다. 디코더는 앱 전체가 **모듈 하나를 공유**하므로 모델마다 지정하지 않고 **진입점에서 기본값 자체를** 바꾼다.
- **파일은 커밋한다**: 설치 스크립트에 복사를 걸어 두면 의존성 버전이 바뀔 때 조용히 갈릴 수 있고, 배포 환경마다 그 훅이 도는지 보장되지 않는다. 복사 스크립트는 두되 **결과물을 레포에 넣어** 받아서 바로 빌드되게 한다.
- **이유**: 폰트를 self-host한 것(030)과 같은 갈래다. 바깥에 기대는 요청이 하나라도 있으면 그 하나가 화면 전체를 세운다.
- **영향**: `scripts/copy-draco.mjs`·`public/draco/`·`lib/draco` 신설. 문 앞에 서면 로비 모델을 미리 받아 둬, 들어갈 때 덮개가 오래 덮여 있지 않게 한다.

### 040. 프로젝트 상세는 데이터가 아니라 페이지 컴포넌트로 두고 번호로 가리킨다

- **날짜**: 2026-08-26
- **상태**: 채택 (012에서 Phase 8로 미뤄 둔 "로컬 상세 데이터"의 확정)
- **맥락**: 012는 `projects`를 Firestore 최소 필드로 두고 `tech`·`images`·`demoKey` 같은 상세를 로컬에 두기로 하되, 실제 형태는 Phase 8에서 정하기로 남겨 뒀다. 전시 칸을 확대해 보여줄 화면을 만들며 그 형태를 정해야 했다. 상세를 로컬 **데이터**(제목·본문·이미지 목록을 담은 객체)로 두고 한 벌의 틀이 그리게 하는 안과, 프로젝트마다 **페이지 컴포넌트**를 두는 안이 있었다.
- **결정**: 상세를 **페이지 컴포넌트의 배열**로 둔다. `contents/<번호>/`에 장마다 컴포넌트를 만들고 `contents/index.ts`가 `번호 → 페이지 목록`을 갖는다. **글도 Firestore가 아니라 여기에 직접 쓴다.** 페이지 컴포넌트는 그 Firestore 문서를 props로 받지만 쓰지 않아도 된다.
- **이유**: 프로젝트마다 보여줄 것이 다르다. 한 프로젝트는 트러블슈팅이 셋이고 다른 프로젝트는 화면 캡처가 전부인데, 이것을 데이터 스키마로 담으려면 장 종류마다 필드를 열거해야 하고 종류가 늘 때마다 스키마와 그리는 쪽을 함께 고쳐야 한다. 컴포넌트로 두면 그 장에 필요한 것만 그 자리에서 그린다. 글을 컬렉션에 두지 않는 것도 같은 이유다 — 줄바꿈·강조·글자 크기까지 화면에 맞춰야 해서 필드로 오가면 손이 더 간다.
- **프로젝트는 번호(`key`)로 가리킨다**: 이름은 바뀌고 한글이라 경로에 인코딩이 붙는다. `key`는 Firestore `projects`의 필드이고, 사진 폴더(`public/images/projects/<key>/`)와 페이지 정의 폴더 이름이 모두 이 값이다. 새 프로젝트를 더할 때 문서에 `key`를 넣는 것이 먼저다 — 없으면 액자는 회색 판으로 남고 페이지는 자리표시가 나온다.
- **Firestore가 맡는 것은 남는다**: 칸 개수, 이름판에 적는 이름, 로비 책의 목록, 그리고 `key`. 개수를 데이터에 맡긴다는 031은 그대로다.
- **되풀이되는 것만 공용으로 뺀다**: 첫 장은 전시 칸마다 형식이 같아 배치를 공용 컴포넌트(`IntroPage`)로 두고 프로젝트 폴더는 글과 링크만 넘긴다. 이미지(`PageIcon`)와 링크(`PageLink`) 컴포넌트도 같은 자리에 있다. 미리 틀을 만들지 않고 장을 만들며 되풀이가 보일 때 옮긴다.
- **장 순서는 고정한다**: 방문자는 칸을 하나씩 열어 보므로 칸마다 구성이 다르면 매번 어디를 봐야 할지 다시 찾는다. 순서는 표준을 두고 장수만 내용에 맞춰 달리한다. 절차·기준은 `docs/PROJECT_PAGES.md`에 둔다.
- **영향**: `contents/` 신설(`index.ts`·`contents.types.ts`·`PlaceholderPages/`·`shared/`·번호 폴더), `docs/PROJECT_PAGES.md` 신설, FIRESTORE의 `projects`에 `key` 추가. 페이지 안 좌표는 월드가 아니라 **가로 1 기준 정규화**라 칸 크기나 방 배율이 바뀌어도 구도가 유지되고, 나중에 인쇄(Phase 9)로 옮길 때도 배율만 갈아 끼우면 된다.

### 043. 복제되는 부품에 개별 내용은 재질이 아니라 앞에 세운 별도 판으로

### 044. 전시 칸 확대 보기: 진행도 블렌드 + 화각 기반 거리

- **날짜**: 2026-08-24

- **맥락**: 액자를 눌러 확대해 보여줘야 하는데, 확대 거리를 상수로 두면 액자 크기나 방 배율이 바뀔 때마다 다시 맞춰야 한다.
